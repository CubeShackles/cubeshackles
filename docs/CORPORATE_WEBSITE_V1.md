# CubeShackles Inc. — Corporate Website V1

Status: implementation brief
Audience: regulators, financial institutions, infrastructure partners, technical evaluators, investors, talent, press
Primary language: English
Localization target: Portuguese (Angola)

## Positioning

CubeShackles Inc. should present as a financial infrastructure technology company, not a consumer crypto project and not a catalogue of speculative future products.

Core message:

> Financial infrastructure engineered for markets where connectivity, institutional complexity, and regulatory requirements cannot be treated as edge cases.

The website should make three ideas immediately legible:

1. CubeShackles builds infrastructure for resilient financial operations.
2. The architecture is designed around constrained-connectivity and reconciliation conditions rather than assuming permanent connectivity.
3. Angola is the initial operating environment; the architecture is intended to support jurisdiction-specific deployment through adapters rather than one generic regulatory model.

## Information architecture

### 1. Home `/`

Hero:
- Eyebrow: `CUBESHACKLES INC. / FINANCIAL INFRASTRUCTURE`
- H1: `Infrastructure for financial systems that cannot afford to stop.`
- Body: `CubeShackles develops resilient financial infrastructure for institutions operating across complex, connectivity-constrained markets. We are building from Angola outward, with reconciliation, auditability and jurisdiction-specific controls designed into the system.`
- CTA 1: `Explore the infrastructure`
- CTA 2: `For institutions`

Trust strip:
`Resilient operations / Reconciliation / Institutional controls / Jurisdiction adapters / Auditability`

Section — The operating reality
Headline: `Permanent connectivity is an assumption. Financial finality cannot be.`
Copy: Explain that intermittent connectivity creates state divergence, delayed synchronization and reconciliation risk. CubeShackles treats degraded-network operation as an architectural condition rather than an exception.

Section — Architecture
Headline: `One infrastructure layer. Jurisdiction-aware deployment.`
Four modules:
- Resilient transaction state
- Reconciliation and ledger controls
- Institutional integration layer
- Jurisdiction adapters

Section — Deployment philosophy
Headline: `Integrate before replacing.`
Copy: Position the system as a non-invasive infrastructure layer designed to coexist with existing institutional systems and reduce migration friction.

Section — Angola
Headline: `Built against a real operating environment.`
Copy: Angola is the initial jurisdiction and engineering reference point. Local financial-system constraints, institutional requirements and connectivity realities inform the architecture.

Section — Institutional CTA
Headline: `Evaluate CubeShackles in a controlled environment.`
Buttons: `Discuss a pilot` / `Developer resources`

- Payment infrastructure operators

`Scope → Sandbox → Integration → Controlled pilot → Production evaluation`

### 4. Angola `/angola`

Use careful wording around BNA, EMIS, payment systems and regulatory engagement. Naming an institution as part of market context must never imply endorsement, partnership, authorization or approval.

## Visual system

Direction: institutional technology, restrained, technical, high-trust.

- Dark graphite/navy foundation
- Warm off-white reading surfaces
- One restrained CubeShackles accent
- Large editorial typography
- Dense technical diagrams balanced by generous whitespace
- Fine grid lines and system-status motifs
- Minimal animation; motion should communicate system state, synchronization or topology
- No generic cryptocurrency imagery, coins, rockets, neon trading screens or stock-photo banking imagery

Reference quality bar: Palantir-level institutional clarity + Stripe-level information hierarchy + Cloudflare-level technical explanation, while retaining a distinct CubeShackles visual language.

## Credibility controls

The site must distinguish these states:
- `Built` — capability exists and can be demonstrated.
- `Pilot` — being evaluated with an authorized counterparty.
- `Research` — technical or market hypothesis.
- `Planned` — roadmap only.

Do not collapse these into a single product catalogue.

Avoid unsupported metrics such as user counts, transaction volume, institutional partnerships, regulatory approval, valuation or market share. Publish them only when substantiated and approved for disclosure.
